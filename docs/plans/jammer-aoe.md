**b. GNSS-only jammer vs B's link symptoms.** Resolution: **the hidden truth is one EW site with two co-located modules.** This is the minimal option.
- **The GNSS module** is a Pole-21E-class module: 300 W, 10 m, 125° sector [VMC envelope]. It drives `gnss_fix` and so the GNSS AoE evidence, and the estimator models only it.
- **The comms module** is R-934B-class: 100–400 MHz [VMC band, Med confidence]. Its EIRP and its co-location are [ASM]. It drives each unit's link J/S, then cadence and CRC through g(·), then the FR-01 / FR-02 trust beats.

Why this option:
1. HS-20 requires B's symptoms to follow from the hidden emitter through a stated link budget. A GNSS jammer cannot raise CRC on a UHF link, so the link symptom needs a link-band emitter.
2. The library entry `ground_based_gps_uhf_barrage` already bundles GPS + UHF (`R-330Zh`, `Pole-21`). A GPS + UHF observation keeps it the **6/6** top match with the FR-04 banner unchanged. A GNSS-only observation would instead match `directional_gps_l1_spot` (L1 only), which would change the top method that FR-04 / FR-04a / UR-09 pin.
3. The rejected **GNSS-health trust component** adds a fifth FR-05 component and re-baselines every pinned beat, which is the High-risk work cut 1 removed.
4. It explains 1:50 honestly. B moves 5 km west and its **GNSS** recovers: it is healthy evidence and the AoE shrinks. Its **link** is still partly jammed (1.8 s / 4%, trust 0.22, still gated), as FR-06 pins.

## 1. Goal and non-goals

**Goal.** The C2 should never show where a jammer *is* when it does not know. Today it does: a hard-coded `JAMMER_LOCATION`, a fabricated bearing line from B and a fixed 120 m ring. Replace these with an honest, deterministic estimate built from friendly observations only.

**MVP (reduced, cleared).** The estimate is:
- a **probability-graded area of effect per GNSS receiver class**: a 50% contour (dashed outline) and a 90% contour (fill and edge). Civil GNSS is drawn on the map (HS-21 / 22 MUST). Military GNSS (DAGR, HS-22 SHOULD) is computed in the same pass and listed in the card, but not drawn (no layer chips);
- the **90% emitter region** as data only (`emitter.region90`, area in the card: *"Emitter not located (90% region ~900 km²)"*). It is not drawn;
- **no emitter symbol and no emitter point**: `mode` is absent from the MVP schema (HS-20; HS-26 is COULD);
- an AoE block on the top candidate card, a two-swatch key, stale / retire handling and an after-action line.

**Method.**
- A soft **set-based grid estimator**. This is the Bayesian grid with a binary probit likelihood. It uses a fixed 250 m ENU grid, a fixed 3 × 3 EIRP × mast hypothesis set from the method's GNSS module, σ = 6 dB, closed-form Φ and ordered summation.
- A **link-budget radius per hypothesis × receiver class**: two-ray plus radio horizon, receiver thresholds from `receivers.json`.
- The **engine computes the polygons**: hand-rolled marching squares, plus simplification to ≤ 64 vertices. The web only draws them, so no new web dependencies are needed (NFR-07).

**Non-goals for the MVP** (each traces to a COULD / WON'T, or was deferred in §0.2):
- bearings / DF / `J1?` (HS-26, v3);
- the NAI graphic (HS-27);
- the TSS advisory (HS-23);
- CoT export (HS-28);
- the UHF / FPV / CRPA / in-flight layers;
- graded C/N0;
- sector fitting (D8);
- terrain / ITM;
- spoofing;
- layer chips, camera-fit and basemap growth;
- the `GET` / dismiss endpoints;
- the method-aware FR-03 radius;
- the library split.

No ML. The R14 discipline holds: identical input gives byte-identical output. The R14 answer: *"a fixed-grid evidence map; each cell's score is a product of published link-budget tests; no training, no learned weights."*
